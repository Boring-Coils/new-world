## 3. 高优先级缺陷

### 3.1 物资锁和产出预留记录会在场景重置前持续残留

**位置**

- `Scripts/Core/MaterialSystem.gd:238`：`take_locked()`
- `Scripts/Core/MaterialSystem.gd:296`：`consume_locked()`
- `Scripts/Core/MaterialSystem.gd:310`：`release_lock()`
- `Scripts/Core/MaterialSystem.gd:433`：`release_reservation()`
- `Scripts/Core/MaterialSystem.gd:573`：`cancel_cycle()`
- `Scripts/Core/MaterialSystem.gd:805`：`_invalidate_inventory_records()`

**问题**

`take_locked(lock_id, carrier)` 在物资进入居民背包后，将锁记录标记为 `closed = true`。取消周期时，`cancel_cycle()` 先通过背包回滚物资，再调用 `release_locks()`；但 `release_lock()` 遇到已经关闭的记录会直接返回，没有从 `_locks` 删除。

`withdraw_items()` 也有同类问题：取出和消耗成功后将锁标记关闭，但没有删除记录。

库存注销时，关联的锁和预留可能只被标记为失效或关闭。后续释放函数遇到关闭记录仍会提前返回，因此记录也无法被清除。

**影响**

- 在单个场景生命周期内，`_locks` 和 `_reservations` 会随取消周期、拆除仓库和即时取用持续增长，直到调用 `start_scene()` 重置账本。
- 当前验收只检查 `get_open_lock_count()` 和 `get_open_reservation_count()`，这两个函数会忽略无效或关闭记录，因此无法发现泄漏。
- `get_tracked_lock_count()` 和 `get_tracked_reservation_count()` 才是能发现该问题的接口，但现有用例没有在取消、取用和库存注销后检查它们。

**建议**

- 成功取消周期后，显式删除该周期的全部锁记录。
- 成功完成即时取用后，删除临时锁记录。
- 库存注销时，主动清除其关联记录，或保证之后所有释放路径都能清除失效记录。
- 为取消周期、即时取用、库存注销和预留失效补充 tracked count 断言。

### 3.2 完成周期后仍藏在站内的居民，离站和死亡清理不完整

**位置**

- `Scripts/Human/Work/HumanWorkBehavior.gd:168`：`cancel()`
- `Scripts/Human/Work/HumanWorkBehavior.gd:365`：成功后设置 `cycle = null`
- `Scripts/Human/HumanAI/HumanAI.gd:540`：`on_employment_ended()`
- `Scripts/Human/Human.gd:79`：`_exit_tree()`
- `Scripts/Building/ScrapSortingStation.gd:36`：站内占用名单

**问题**

工作周期成功结算后，居民按设计继续隐藏在站内，此时 `cycle` 已经为 `null`。

如果此时工作站被拆除：

1. `Building` 解雇雇员。
2. `HumanAI.on_employment_ended()` 调用工作周期取消。
3. `HumanWorkBehavior.cancel()` 发现 `cycle == null` 后提前返回。
4. `_leave_host_building()` 不会执行，居民不会恢复显示。
5. 工作站随后被释放，居民的 `in_building` 引用失效。

如果居民在工作站内死亡，工作站没有同步清除 `occupants`，可能持续保留失效居民引用。

**影响**

- 拆除工作站后，居民可能永久不可见。
- 之后普通移动不会调用离站逻辑，因此不会自动恢复显示。
- 工作站占用数量可能与实际居民不一致，产生悬空引用。

**建议**

- 即使 `cycle == null`，离站和销毁清理也应确保清理 `in_building`。
- `on_employment_ended()` 应作为兜底执行离站、清空占用和恢复显示。
- 补充“工作完成后拆除工作站”和“工作完成后居民死亡”的验收项。

### 3.3 产出空间预留不能保证周期可以结算

**位置**

- `Scripts/Core/MaterialSystem.gd:403`：`reserve_output()`
- `Scripts/Core/MaterialSystem.gd:511`：`settle_cycle()`
- `Scripts/Core/MaterialSystem.gd:480`：`replace_invalid_reservations()`
- `Scripts/Human/Work/HumanWorkBehavior.gd:90`：开始周期时的产出预留调用

**问题一：体积足够但不满足单件体积**

系统只预留总体积，没有考虑目标库存能否容纳一个不可分割的物品。

可复现示例：

1. 两个仓库容量各为 `1`。
2. 工作产出为 1 个废料，废料单件体积为 `2`。
3. `reserve_output(2)` 会在两个仓库各预留 `1` 体积并报告成功。
4. `settle_cycle()` 无法把体积为 `2` 的废料放入任何容量为 `1` 的目标。
5. 两份预留的总体积仍等于目标体积，`replace_invalid_reservations()` 会认为预留有效，不会重新整理。

结果是周期可能永久停留在待结算。

当前默认的废料分拣工作产出为金属、塑料和线材，单件体积均为 `1`，因此该示例暂时不会被默认配方触发；问题位于通用 `WorkType` 和物资预留接口，新增体积大于 `1` 的产出时会暴露。

**问题二：输入仍占用容量时过早预留产出**

`begin()` 先锁定需求并预留产出空间，之后才把雇主库存中的需求取入居民背包。

可复现示例：

1. 雇主库存容量为 `2`，当前有两项各占 `1` 体积的物资，且没有其他可用仓库空间。
2. 本轮需求占 `1` 体积，产出占 `1` 体积。
3. 消耗需求后，库存只剩 `1` 体积占用，产出可以正常放入。
4. 但在消耗需求前执行产出预留时，库存没有可用体积，周期被错误拒绝。

当前默认废料分拣站自带库存容量为 `1000`，默认场景通常不会触发该容量边界；该问题主要影响后续新增的小容量工作站或自定义工作配置。

**影响**

- 空间的错误接受会导致永久待结算。
- 空间的错误拒绝会让本可执行的周期无法开始。
- 设计文档声称空间预留保证周期能够结算，当前实现没有完全满足该契约。

**建议**

- 预留时检查目标仓库能否按单件体积实际分配产出。
- 结算前允许重新打包现有预留，而不是只比较总体积。
- 先完成输入取货再预留产出，或在容量计算中扣除即将消耗的输入体积，并在失败时完整回滚。
- 增加不可分割物品跨多个小仓库的验收场景。

## 4. 中优先级缺陷

### 4.1 Buff 判定死亡后，居民同一刻仍继续消费和行动

**位置**

- `Scripts/Buff/Types/Weakness.gd:29`
- `Scripts/Buff/BuffSystem.gd:113`
- `Scripts/Human/Human.gd:127`

**问题**

虚弱 Buff 到期时会在 `on_remove()` 中调用 `human.die()`，但 `Human.on_tick()` 随后仍会继续执行基础水食消耗和 `ai.on_tick()`。

**影响**

居民虽然已经排入删除队列，仍可能在死亡当刻移动、取料或结算一次工作周期。

**建议**

在 Buff 推进后、基础消耗和 AI 推进前检查 `is_queued_for_deletion()`。

### 4.2 取料或返岗期间下班，不会立即结束准备中的周期

**位置**

- `Scripts/Human/HumanAI/HumanAI.gd:511`
- `Scripts/Human/Work/HumanWorkBehavior.gd:295`

**问题**

准备阶段只检查紧急口渴、饥饿和 Buff 硬中断，不检查班次是否已经结束。

居民可能在 1500 刻以后继续前往外部仓库取料，持续持有需求锁和产出预留，直到返回雇主并进入 `_start_locked()` 才取消周期。

**影响**

- 下班后仍进行无意义的跨仓库移动。
- 物资锁和预留空间被继续占用。
- 与设计文档“班次结束仍未取得完整需求时，不开始周期并释放锁定”不一致。

**建议**

在非锁定阶段每刻检查 `employer.is_work_time()`，班次结束立即取消准备周期。

### 4.3 完整验收基线与当前代码不一致

**位置**

- `Scripts/Debug/AcceptanceSelfTest.gd:538`
- `Scripts/Human/Human.gd:124`
- `Scripts/Debug/AcceptanceSelfTest.gd:2272`
- `Scripts/Building/Building.gd:545`
- `Docs/当前实现状态.md`

**问题**

连续 6 次执行完整验收，结果均为 `101/103`。

`SCH-06`：

- 验收使用 `offset.length() > 5.0` 判断是否超过半格。
- 实现分别将 X、Y 限制在 `[-4, 4]`。
- 当前样本 `(3.088, 3.96)` 的欧氏长度约为 `5.02`。
- 这是验收断言和偏移生成规则不一致，不是单纯的随机偶发失败。

`UI-03`：

- 验收查询板块 `inventory`，实际板块 ID 是 `inventoryTotal`。
- 仓库详情没有“可用体积”行。
- 修正其中一项仍不足以让该断言通过。

`Docs/当前实现状态.md` 仍写 `102/103`，与实际结果不符。

**建议**

- 明确“半格”是单轴限制还是欧氏距离限制，并统一实现、测试和文档。
- 修正 `UI-03` 的板块 ID，并决定是否显示“可用体积”。
- 更新当前验收基线。

### 4.4 Blender 居民生成脚本写死错误项目路径

**位置**

- `Tools/Blender/make_human.py:27`

**问题**

脚本将项目目录写死为：

```python
PROJECT = r"H:\Projects\new-world"
```

当前仓库位于：

```text
D:\Projects\new-world
```

按照脚本标注的命令运行，会写入错误磁盘或直接失败。

脚本顶部声明的产物路径也与实际 `side/down/up` 子目录结构不一致。

**建议**

从 `__file__` 推导仓库根目录，并同步修正产物目录说明。

## 5. 低优先级问题

### 5.1 声明为永久的 Buff 实际只持续一刻

**位置**

- `Scripts/Buff/BuffBase.gd:17`
- `Scripts/Buff/BuffSystem.gd:113`

`duration = -1` 的文档语义是永久 Buff，但系统每刻无条件执行 `duration -= 1`，随后在 `duration <= 0` 时移除。

当前具体 Buff 都显式设置了正持续时间，因此尚未直接暴露，但基类契约已经失效。

### 5.2 工作站拒绝入住时仍被视为进入锁定周期

**位置**

- `Scripts/Human/Work/HumanWorkBehavior.gd:310`

`_start_locked()` 忽略 `employer.enter(human)` 的返回值，即使入住失败也会继续锁定并推进工作。

当前 `ScrapSortingStation.enter()` 总是返回 `true`，但通用 `Building.enter()` 接口允许返回失败。

### 5.3 已放置建筑调用旋转接口后，网格占用不会同步

**位置**

- `Scripts/Building/Building.gd:198`

`set_rotation_steps()` 允许已经放置的建筑改变占格和出入口，但不会更新世界网格中的不可走格子。

当前放置流程只在提交前旋转预览，因此尚未直接触发；作为公开接口，之后如果给已放置建筑增加旋转功能，会造成旧占格和新占格不一致。

### 5.4 数字输入框获得焦点时，整个详情页停止刷新

**位置**

- `Scripts/UI/BuildingDetailPanel.gd:214`

结构签名变化且输入框持有焦点时会直接返回。这样虽然避免了重建焦点控件，但库存数量等不需要重建的文本也不会更新。

### 5.5 场景关闭判断存在绕过

**位置**

- `Scripts/Core/MaterialSystem.gd:656`

`cleanup_owner_inventory()` 直接检查 `_scene_shutdown`，没有调用专门识别“当前场景已排进删除队列”的 `is_scene_shutdown()`。

场景整体退出时，仍可能尝试把物资路由到其他库存，违反“场景关闭只清空数据”的契约。

### 5.6 存在孤立的脚本 UID

**位置**

- `Scripts/Material/CarryBag.gd.uid`

对应的 `Scripts/Material/CarryBag.gd` 已不存在，实际脚本位于 `Scripts/Human/CarryBag.gd`。

该文件目前不阻止项目加载，但属于残留资源，应清理或确认 UID 是否需要迁移。

## 7. 建议处理顺序

1. 修复物资锁和预留记录泄漏，并扩展 tracked count 验收。
2. 修复完成周期后的离站、拆除和死亡清理，消除不可见居民和悬空占用。
3. 重做产出预留的可用性判断，保证“预留成功即可结算”。
4. 修复死亡后同刻继续行动和下班后继续准备周期。
5. 修正 `SCH-06`、`UI-03` 及当前验收基线。
6. 处理 Blender 路径和其余低优先级契约问题。
