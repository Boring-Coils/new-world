# 04 迁移、测试与验收

## 1. 迁移目标

把旧居民 AI 从“一个类同时管理决策、路径、移动、等待和表现”迁移为：

```text
Human 调度
└─ HumanAI 决策与协调
   └─ StateChart 单动作状态机
      └─ HumanMotion 执行移动
```

迁移不是保留旧 AI 再增加状态机。完成时必须删除旧 `Goal/Phase/move/path` 实现，
避免两套逻辑同时推进居民。

## 3. 实施顺序

### 阶段 0：建立可回退基线

先确认当前失败日志和工作区状态：

```powershell
git status --short
git diff --check
godot --headless --path . --import
godot --headless --path . Scenes/TestScene.tscn -- --speed=20 --max-ticks=60
```

预期能看到当前已知的 `HumanAI._init` 参数错误。把它记录为基线，不要误判成新实现的问题。

### 阶段 1：补齐组件所有权

目标：

- `Human.tscn` 增加 `Motion`。
- `Human` 不再创建 AI，改为引用场景节点。
- Motion 到 Visual 的信号连接完成。
- `Human.in_building` 在进入工作站时有唯一写入点。

本阶段可以先保留旧 AI 内部实现，但必须保证每刻只有一个 AI 节点被调用。

验证：

- 场景实例化不报 `_init` 参数错误。
- `TickManager.humans` 中每个居民只有一个 AI。
- 空闲居民不会自行移动。
- 初始状态 deferred 激活前请求脱困，不会丢事件。

### 阶段 2：完成 Motion 契约

目标：

- 所有会创建移动状态的命令失败时发出一次 `path_failed`；
  查询命令和脱困命令不走该信号，脱困失败由返回值和调用方兜底。
- 脱困 no-op 发出 `relocation_finished`。
- 从站内到目标失败时不改变 `in_building`、位置和显示。
- 从站内到目标成功时在同一同步调用内原子离站。

验证：

- 站内居民前往不可达目标后仍属于工作站。
- 离开工作站时有且只有一次 `building_exited`。
- `Moving` 用例不会永久等待。

### 阶段 3：实现纯决策模块

目标：

- 新增 `HumanAIContext.gd`。
- 新增 `HumanDecision.gd`。
- 用固定测试数据验证评分、平手、消耗倍率、逐刻直接扣减和工作闸门。

此阶段不接入真实状态机，可先在静态函数上做日志断言。

### 阶段 4：替换 `HumanAI`

目标：

- `HumanAI` 成为 `Node` 协调器。
- 绑定场景状态节点。
- 状态脚本覆写 `_ready()` 时调用插件基类 `super._ready()`。
- `on_tick()` 推进一次状态机、一次 Motion。
- 实现取水、取食、工作、等待、脱困。

此时会删除旧 `Phase`、路径字段和旧移动函数。

## 4. 测试分层

项目没有单元测试框架，因此分三层：

1. 纯函数日志断言：决策排序、平手、工作闸门。
2. 无头集成运行：TestScene 常规、放置、Buff、长跑。
3. 编辑器人工检查：状态图、视觉、工作站进出、放置交互。

不要只用命令退出码判断成功。Godot 脚本错误可能仍以 0 退出。

### 5.1 导入与静态检查

```powershell
godot --headless --path . --import

```

- 没有 `Method expected` 参数错误。
- 没有状态机 configuration warning。
- 没有未知事件警告。

### 5.2 常规模拟

```powershell
godot --headless --path . Scenes/TestScene.tscn -- --speed=20 --max-ticks=600
```

检查：

- 居民能进入 `idle`、`traveling`、`waiting`、`working`。
- 居民能完成取水、取食。
- 工作后能因需求中断。
- 没有居民永久停在 `traveling`。
- 路径长度和位置持续变化，不出现路径已空但状态仍为 `traveling`。

### 5.3 放置与脱困

```powershell
godot --headless --path . Scenes/TestScene.tscn -- --autoplace --speed=20 --max-ticks=60
```

检查 `[AUTOPLACE]`：

- 非法放置仍失败且不注册。
- 建筑压住居民后 `relocating == true` 或位置发生变化。
- 脱困完成后回到 `idle`。
- 不出现隐身后无人恢复显示。

### 5.4 Buff 工作闸门

```powershell
godot --headless --path . Scenes/TestScene.tscn -- --bufftest --speed=20 --max-ticks=140
```

检查：

- 眩晕期间不会新选 `WORK`。
- 已在工作的居民被眩晕后离开工作站。
- 前往或等待工作站时被眩晕，会停止工作目标并回空闲。
- 疲劳速度仍从 Motion 读取并乘入。
- 口渴实际扣水量与上报给决策上下文的逐刻速率一致，计时和到期不受状态机影响。

### 5.5 长时间运行

```powershell
godot --headless --path . Scenes/TestScene.tscn -- --speed=20 --max-ticks=5400
```

至少跑满三个游戏日，检查：

- 补水、补食循环持续。
- 目标建筑引用没有失效泄漏。
- 没有每刻日志刷屏。
- 没有状态图无限循环错误。

### 5.6 建议新增 `--aitest`

当前测试日志只能人工阅读。建议在实现阶段增加一个专用调试模式：

```powershell
godot --headless --path . Scenes/TestScene.tscn -- --aitest --speed=20 --max-ticks=300
```

`HumanAISelfTest` 至少检查：

| 用例 | 期望 |
| --- | --- |
| AI 实例数 | 每个居民恰好 1 个 |
| Motion 实例数 | 每个居民恰好 1 个 |
| 状态空闲 | 无目标时 `state == idle` |
| 状态基类初始化 | 首次转换不出现 `_chart` 空引用错误 |
| 初始化窗口脱困 | 初始状态激活前请求的脱困在首个有效 tick 执行 |
| 路径失败 | `traveling` 在一个 tick 内回 `idle` |
| 工作闸门 | `can_work == false` 时 `Traveling`、`Waiting`、`Working` 都不会保留 `goal == WORK` |
| 有效消耗 | 消耗倍率或 `Thirst` 直接扣减变化后，资源紧迫刻数随之变化 |
| 工作站内换目标失败 | `in_building` 仍为原站 |
| 工作站内换目标成功 | 离站后 `in_building == null` 且可见 |
| 站内脱困 no-op | 即使脚下可走，也清空 `in_building`、离开占用名单并恢复可见 |
| 脱困完成 | 最终 `state == idle` |
| 脱困失败 | 无安全格时产生 `relocation_failed` 和错误日志，不伪装成完成信号 |

该模式可以继续使用项目现有风格：打印“期望 / 实际”，但最终应汇总一个明确的
`[AITEST] PASS/FAIL`，减少只靠肉眼逐行扫描的负担。

无头测试无法验证以下内容：

## 8. 性能检查

本版目标是原型规模，但仍要避免明显浪费：

- `HumanDecision` 每 5 刻左右运行一次，不每 tick 排序。
- 建筑扫描只在选择目标时发生。
- 状态机每 tick 只 step 一次。
- Motion 每 tick 只推进一次。
- 状态脚本不做日志刷屏。
- 不使用每居民独立 `Timer` 或 `_process`。

已知可接受开销：

- `find_nearest_building()` 会计算一次路径，随后 `move_to_building()` 可能再次计算
  同一路线。当前居民数量下可接受。
- 若以后居民数量明显上升，应给 `HumanMotion` 增加“规划并提交同一路线”的接口，
  而不是让 AI 接触路径细节。

## 9. 风险与处理

| 风险 | 表现 | 处理 |
| --- | --- | --- |
| 场景 AI 和代码 `new` 并存 | 每 tick 决策两次 | 只使用 `$HumanAI` |
| Motion 和旧 AI 同时移动 | 一 tick 走两步 | 删除旧移动，AI 单一调用 Motion |
| 状态等待用帧延迟 | 倍速下等待错误 | 状态脚本按 `step()` 递减 |
| 路径失败无信号 | 卡在 Traveling | 会创建移动状态的命令必发 `path_failed`；查询和脱困命令除外 |
| 脱困 no-op 无信号 | 卡在 Relocating | 成功 no-op 也发完成信号 |
| 站内脱困 no-op 未离站 | 状态回到 Idle，但居民仍隐身并保留占用 | 发完成信号前执行 `_commit_building_exit()` |
| 脱困失败冒充完成 | 日志看似成功，居民仍在不可走格 | 失败走 `relocation_failed` 并输出错误 |
| 工作闸门只查下一次决策 | 眩晕后仍前往或留在工作站 | 工作目标处于 `Traveling/Waiting/Working` 时每 tick 检查 |
| 回到空闲仍保留旧目标 | 路径失败后显示错误目标或反复选择 | `Idle` 进入时清空 `_goal/_target` |
| 状态基类未初始化插件字段 | 首次转换出现空 `_chart` | `HumanStateBase._ready()` 调用 `super._ready()` |
| 初始状态未激活时发脱困事件 | 请求被状态图丢弃，居民不脱困 | AI 暂存到 `_active_state_key` 非空后再发 |
| 决策忽略有效消耗 | 虚弱或口渴时紧迫度失真 | Context 合并基础消耗、倍率和逐刻直接扣减 |
| 离站前提前隐藏/显隐 | 视觉抖动或站内显示 | HumanMotion 单次同步提交 |
| 工作状态未设 `in_building` | 无法原子离站 | 只在 `enter_current_workstation()` 写入 |
| 重复连接信号 | tick 内多次转换 | `bind()` 幂等并检查 `is_connected` |
| 事件拼写不一致 | 状态不切换 | `StringName` 常量 + 未知事件警告 |
| 迁移测试仍读旧字段 | 无法编译或语义错误 | 统一改用调试快照 |

## 10. 完成定义

只有以下条件全部满足，才能把重构标记为完成：

### 10.1 结构

- [ ] `Human.tscn` 只有一个 `HumanAI`、一个 `Motion`。
- [ ] `HumanAI` 下只有一棵状态图。
- [ ] 所有动作状态有独立脚本。
- [ ] 所有状态脚本通过 `HumanStateBase._ready()` 调用插件 `super._ready()`。
- [ ] `Brain.gd` 与 `StatusBase.gd` 不再参与运行。
- [ ] 没有旧 `HumanAI.new(host)` 调用。

### 10.2 行为

- [ ] 取水、取食、上班、等待、脱困都能闭环。
- [ ] 工作闸门在前往、等待和站内三个阶段立即生效。
- [ ] 进入 `Idle` 时清空残留目标和路径。
- [ ] 初始状态激活前的脱困请求不会丢失。
- [ ] 工作站内换目标保持原子性。
- [ ] 路径失败和脱困 no-op 都不会卡状态。
- [ ] 脱困无安全结果时走失败事件，不发送成功完成信号。
- [ ] 同一刻只移动一次。
- [ ] 进入工作站设置 `in_building`，离开时清空并恢复显示。

### 10.3 接口

- [ ] `Human.on_tick()` 只调用一次 `HumanAI.on_tick()`。
- [ ] AI 不访问 `WorldGrid`、路径索引或居民坐标。
- [ ] AI 和状态脚本不直接调用 `hide()` / `show()`。
- [ ] 外部使用 `get_debug_snapshot()`，不读 `_goal`、`_active_state`。
- [ ] Placement 只调用 `Human.relocate_out()`。
- [ ] Buff 自测从 Motion 获取速度。

## 11. 后续扩展

稳定后可以按以下顺序扩展：

1. 工作站班次、容量和排队。
2. 任务系统，统一表达取水、取食、工作和建造任务。
3. 目标预约，避免多个居民抢占同一容量。
4. 状态机存档与恢复。
5. 更丰富的决策因子，例如距离、关系、需求和优先级。
6. 多类居民使用同一状态图模板，但通过决策配置区分。

在这些扩展进入前，不要先破坏本版的两个核心不变量：

> 同一刻只有一个组件推进移动。
>
> 同一居民同一时间只有一个主动作状态。
