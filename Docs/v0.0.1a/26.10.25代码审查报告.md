> 再继续 v0.0.1c 的拆除、状态栏和存档功能。**

## 二、详细发现

### R-07 [P1] 虚弱 Buff 痊愈后不会被移除

**位置**

- `Scripts/Buff/Types/Weakness.gd:13-17`：痊愈时把 `duration` 设为 `0`。
- `Scripts/Buff/BuffSystem.gd:108-116`：只有 `duration > 0` 时才扣时长并移除。
- `Scripts/Human/Human.gd:72-73`：水或食物耗尽时重复添加虚弱。

**问题**

`Weakness.on_tick()` 在 `heal_time <= 0` 时执行 `duration = 0`，但
`BuffSystem.on_tick()` 的判断顺序是「先 `on_tick()`，再检查
`if buff.duration > 0`」。当 `Weakness` 自己把 `duration` 改成 `0` 后，
这次 `BuffSystem` 的 `if` 直接不成立，既不扣时长也不调用
`remove_buff()`，Buff 会永久留在身上。

**验证结果**

给一个居民挂上虚弱，连续 9000 刻保持水和食物都高于 200：

```text
[PROBE] has_weakness=true duration=0 heal_time=0 can_work=false
```

即：按文档已经满足 5 个游戏日的痊愈条件，但虚弱仍在，
`can_work()` 仍为 `false`，消耗倍率也一直保持 `0.5`。

**影响**

这是虚弱规则的核心回归：居民一旦虚弱，即使水和食物恢复充足，也永远不会
恢复工作能力；同时永久只消耗一半水和食物，行为和玩家看到的数值完全脱节。

**建议**

不要用 `duration = 0` 表示到期。可以改成 `duration = 1`，让
`BuffSystem` 在本刻扣到 0 后正常走 `remove_buff()`；更稳妥的做法是让
`BuffSystem.on_tick()` 在 `on_tick()` 返回后统一检查
`duration <= 0` 并移除，这样以后其它 Buff 也能安全地在自己的逻辑里结束自己。

### R-08 [P1] 拆除按钮调用空实现 `Building.remove()`

**位置**

- `Scripts/Building/Building.gd:437-439`：`remove()` 只打印 `"remove"`。
- `Scripts/UI/BuildingDetailPanel.gd:128-135`：按钮点击后收起面板并调用它。

**问题**

详情页已经加入了「摧毁建筑」按钮，但 `Building.remove()` 仍是占位实现。
点击按钮后只会关闭面板并打印一行日志，建筑不会离开场景，占格不会释放，
`TickManager.buildings` 不会移除，正在以它为目标的居民也不会重新决策。

**验证结果**

放置一栋取水站后直接调用 `remove()`：

```text
remove
[PROBE] demolish placed=true registered=true body_walkable=false queued_for_deletion=false
```

建筑仍在 `TickManager.buildings` 中，本体格子仍不可走，节点也没有被释放。

**影响**

这是 v0.0.1c 拆除需求的主入口，当前功能完全不可用。玩家点击「摧毁建筑」
只会看到面板关闭，没有任何拆除反馈；后续如果只补 `queue_free()` 而忘记
释放网格和注销登记，还会留下永久不可走的建筑占格。

**建议**

按需求实现完整拆除流程：把站内居民赶出、释放所有本体占格、从
`TickManager` 注销、关闭详情页、释放节点，并让目标为该建筑的居民重新决策；
最后发出一句「XXX 已拆除」的提示。

### R-09 [P2] 虚弱在 `heal_time == 0` 时仍判定死亡

**位置**

- `Scripts/Buff/Types/Weakness.gd:19-21`：`if heal_time >= 0: human.die()`。

**问题**

`heal_time` 从 9000 开始，每满足一刻充足条件减 1；减到 `0` 表示刚好完成
5 个游戏日的痊愈。此时 `on_remove()` 仍满足 `heal_time >= 0`，会调用
`human.die()`。死亡判断应当只在「尚未痊愈」时成立，即 `heal_time > 0`。

**验证结果**

在虚弱居民的 `heal_time` 刚好减到 0 时手动移除 Buff：

```text
[PROBE] after_manual_remove queued_for_deletion=true valid=true
```

居民被排队删除，而不是痊愈。

**影响**

R-07 当前让 Buff 永远不会被移除，所以这条死亡分支暂时被掩盖；一旦按
R-07 的建议修好移除逻辑，刚好在第 5 天痊愈的居民会立即死亡，痊愈规则仍然
不成立。两个问题需要一起修。

**建议**

把条件改成 `if heal_time > 0: human.die()`；如果希望死亡只在「10 天计时
到期」时发生，更清晰的做法是单独记录死亡倒计时，不要用 `on_remove()` 表达死亡。

### R-10 [P2] 拆除没有二次确认和结果提示

**位置**

- `Scripts/UI/BuildingDetailPanel.gd:128-135`：第一次点击就关闭面板并拆除。

**问题**

`Docs/v0.0.1c/需求文档.md` 的拆除交互要求「点一次变『确认拆除？』，再点一次
才真的拆；中途点别处或关面板则取消」，并在拆除后提示「XXX 已拆除」。
当前按钮没有确认状态，也没有成功/失败提示，属于破坏性操作的一击即中。

**影响**

等 R-08 补上真正的删除逻辑后，玩家误点一次就会永久拆掉建筑；需求明确要求
防误触，当前实现不满足验收条件。

**建议**

给按钮加两段式状态：第一次点击只改文案为「确认拆除？」并进入待确认状态，
第二次才调用拆除；面板关闭、点击空白处或切换到其它建筑时重置状态。拆除成功后
通过 `PlacementController.notice` 或独立 signal 显示结果提示。

### R-11 [P3] 虚弱痊愈/死亡时长硬编码 `1800` / `18000`

**位置**

- `Scripts/Buff/Types/Weakness.gd:4`：`heal_time: int = 1800 * 5`。
- `Scripts/Buff/Types/Weakness.gd:7`：`duration = 18000`。

**问题**

项目约定每日刻数由 `TickManager.TICKS_PER_DAY` 统一控制，文档也写明修改
该常量后每日消耗、速度和补给提前量会自动跟随。弱虚这里直接写死 1800 和
18000，一旦调整一天刻数，5 天痊愈和 10 天死亡的规则就会偏离。

**影响**

当前 `TICKS_PER_DAY` 恰好是 1800，所以不影响现有运行；但这是一处隐藏的
耦合，后续调整时间尺度时会出现「虚弱恢复比其它系统快/慢」的问题。

**建议**

改成 `TickManager.TICKS_PER_DAY * 5` 和 `TickManager.TICKS_PER_DAY * 10`
（或在 Weakness 内定义两个按天计算的常量），与项目其它按天计时逻辑保持一致。

### R-12 [P3] `v0.0.1c/需求文档.md` 标题仍写 `v0.0.1b`

**位置**

- `Docs/v0.0.1c/需求文档.md:1`：`# v0.0.1b 需求文档`。

**问题**

提交 `2697765` 把文件从 `Docs/v0.0.1b/` 移到 `Docs/v0.0.1c/`，但没有更新
文档标题；同时 `project.godot` 的版本是 `0.0.1.2`，三处版本标识不一致。

**影响**

不影响运行，但会让后续查需求和对照提交时误判当前目标版本。

**建议**

把标题改为 `v0.0.1c`，并在版本记录中补一行本次迁移说明；如果项目版本号
`0.0.1.2` 是有意采用的构建号，建议在文档中说明它与 `v0.0.1c` 的对应关系。

5. 为虚弱痊愈、虚弱死亡、拆除后网格释放/目标重选补最小的 headless 验证；
   现有 `BuffSelfTest` 只覆盖疲劳、眩晕、口渴，无法发现本轮问题。
