# v0.0.1a 代码审查报告

> 审查对象：`master` 当前代码（HEAD `858905f`，v0.0.1a 实现）
> 审查范围：`Scripts/`、`Scenes/`、`Tools/Blender/make_human.py`，并对照
> `Docs/总/` 与 `Docs/v0.0.1a/` 中的规则文档
> 审查方式：静态阅读、Godot 4.7 headless 运行、临时诊断场景验证
> 结论：**当前代码存在 1 个核心规则回归和 3 个会导致居民卡死/穿模的放置问题，
> 建议在进入 v0.0.1b 前修复。**

## 一、结论摘要

| 编号 | 优先级 | 问题 | 主要影响 |
| --- | --- | --- | --- |
| R-01 | P1 | 水/食物降到 0 以下后不再进入虚弱状态 | 与 `Docs/总/资源`、`Docs/总/状态` 的核心规则不符；居民会继续正常工作、正常行动 |
| R-02 | P2 | 新建筑本体可以盖住已有建筑的出入口 | 旧建筑的出入口变成不可走，居民仍会选中它，寻路失败后原地闲置 |
| R-03 | P2 | 选目标只看直线距离，不检查可达性，也没有备选回退 | 最近的水站/食物站不可达时，居民不会去更远但可达的同类建筑，可能永久挨饿 |
| R-04 | P2 | 居民不会因路径中途出现新建筑而重新寻路 | 居民会直接穿过刚放下的建筑，放置结果与寻路状态不一致 |
| R-05 | P3 | 放置失败时建筑已先加入场景并注册 | 失败建筑会在当帧残留于 `TickManager.buildings`，可能被居民当成目标 |
| R-06 | P3 | 权重平手时的优先级与注释相反 | 水/食物刚好在 36 分钟阈值时，工作优先，补给会晚 5 刻 |

## 二、详细发现

### R-01 [P1] 水/食物耗尽后不再进入虚弱状态

**位置**

- `Scripts/Human/Human.gd:168-172`：`_consume()` 只扣数值，没有任何状态判断。
- `Scripts/Enum/GlobalEnum.gd:24-30`：`BuffType` 只有 `FATIGUE`、`STUN`、`THIRST`，没有 `WEAK`。
- `Scripts/Buff/BuffSystem.gd:22-26`：`REGISTRY` 也没有虚弱 buff。

**问题**

提交 `a1caed1`（“虚弱状态改由 buff 管理”）删除了 `Human` 原来的
`is_weak` 判断和“水/食物小于 0 就停止行动”的逻辑，但没有补上 `Weak` buff。
现在 `_consume()` 恢复后不会触发任何状态，`Human` 顶部注释里说的
“虚弱、受伤这类状态统一由 BuffSystem 管理”实际上没有对应实现。

**验证结果**

在临时诊断场景中把居民的水和食物都设为负值后调用 `_consume()`：

```text
starved buffs=0 can_work=true water=-10.94 food=-11.06
```

即：水/食物已经为负，但居民没有任何 buff，仍然 `can_work=true`。

**影响**

`Docs/总/资源/水资源.md:7`、`Docs/总/资源/食物.md:7` 明确规定“小于 0 进入
虚弱状态”，`Docs/总/状态/单人状态/虚弱.md:2` 规定虚弱时不能工作。当前实现
让这条核心规则完全失效；玩家看到的是居民饿着/渴着仍然照常上班，或者在没有
可达补给站时只是原地待着，没有任何虚弱反馈。

**建议**

恢复虚弱状态：新增 `GlobalEnum.BuffType.WEAK` 和对应 buff，注册到
`BuffSystem.REGISTRY`，并在 `Human._consume()` 扣完数值后检查
`water < 0.0 or food < 0.0` 时调用 `buff_system.add_buff(WEAK)`。虚弱 buff
至少需要让 `can_work()` 返回 `false`，并按当前 v0.0.1a 的范围只做“停止工作/
停止行动”，死亡、医院和治疗留到后续版本。

### R-02 [P2] 新建筑本体可以盖住已有建筑的出入口

**位置**

- `Scripts/Building/Building.gd:159-163`：只检查新建筑本体格子是否 `is_walkable`。
- `Scripts/Building/Building.gd:165-176`：只检查新建筑自己的出入口。
- `Scripts/Human/Human.gd:301-308`：寻路到出入口失败后直接 `_go_idle()`。

**问题**

已有建筑的出入口格子本身是 `walkable` 的，因此 `can_place_at()` 允许把另一栋
建筑的本体直接盖在这个出入口上。放置后 `place_at()` 会把这些格子设为不可走，
但旧建筑的 `get_entrance_cells()` 仍然返回原来的出入口，`get_nearest_entrance_cell()`
也仍然可能选中它。

**复现结果**

临时诊断场景中先放一个 4×3 取水站，再在它的出入口 `(11,13)` 上放另一栋
4×3 建筑：

```text
water entrance before=true
... placed over water entrance=true
water entrance after=false
path=[]
nearest entrance=(11, 13)
```

第二次放置返回 `true`，但旧水站出入口已经不可走，从空地到该出入口的路径为空。

**影响**

玩家可以合法地“堵死”已有建筑，居民仍会按旧出入口寻路，失败后进入闲置；
如果这是唯一的取水/取食站，居民会一直无法补给。该问题也会放大 R-03。

**建议**

放置前检查新建筑本体是否覆盖任何已有建筑的出入口，覆盖时拒绝放置；或者把
出入口格子单独登记为“保留区”，不参与普通空地判断。若允许覆盖，则必须在
放置后同步更新旧建筑的出入口状态并让正在前往的居民重新选目标。

### R-03 [P2] 选目标只看距离，不检查可达性，也没有备选回退

**位置**

- `Scripts/Human/Human.gd:315-326`：`_find_nearest_building()` 用切比雪夫距离
  选最近建筑，不计算路径。
- `Scripts/Human/Human.gd:301-308`：只尝试 `get_nearest_entrance_cell()` 给出的
  一个出入口；路径为空就 `_go_idle()`。

**问题**

`_start_goal()` 只尝试最近建筑最近的一个出入口。该出入口可能被建筑封住、
被墙围住，或者路径被其他建筑切断；此时代码不会尝试同一栋建筑的其他出入口，
也不会尝试下一栋同类建筑，而是直接清空目标。下一次决策仍会选中同一个最近
建筑，形成永久循环。

**复现结果**

临时诊断场景中放两个取水站，把较近水站的出入口设成不可走，较远水站可达：

```text
near entrance=(101, 103) walkable=false
far entrance=(201, 203)
path near=[]
path far=[...]
after start goal: goal=0 phase=0 target=<null>
```

居民选择了近处水站，寻路失败后回到 `IDLE/NONE`，没有改选远处水站。

**影响**

只要玩家封住或围住最近的同类建筑，居民就会永久闲置；这是比“走远一点”更严重
的逻辑错误，也会让 R-02 的后果从“一栋建筑不可用”扩大为“居民不再补给”。

**建议**

按距离从近到远枚举同类建筑及其全部出入口，逐个尝试 `get_path()`，使用第一个
可达路径；或者直接用“到最近可达出入口”的搜索。找不到可达目标时再闲置。

### R-04 [P2] 居民不会因路径中途出现新建筑而重新寻路

**位置**

- `Scripts/Human/Human.gd:393-399`：`_move()` 只按 `path` 中的下一个格子做
  线性插值，不检查该格是否仍然 `is_walkable`。
- `Scripts/World/PlacementController.gd:162-176`：`_evict_humans_in()` 只处理
  当前正好站在新建筑占地格上的人。

**问题**

居民在 `_start_goal()` 时算好一条路径后，`_move()` 会无条件沿路径走完。玩家在
居民移动途中把建筑放在路径的后续格子上时，居民不会重新寻路，也不会被
`_evict_humans_in()` 挤出来，因为放置时居民当前格还不在建筑里。

**复现结果**

让一个居民沿 `(300,300) -> (310,300)` 移动，并在路径中间 `(305,300)` 放一栋
4×3 建筑。建筑放置成功后继续调用移动逻辑，居民最终仍然到达 `(310,300)`，
中间直接穿过了不可走的建筑格。

**影响**

这是明确的穿模和规则不一致：建筑已经占格并设为不可走，但居民仍能从建筑内部
穿过。继续扩展放置、拆除功能时，这种“旧的路径引用”还会导致更多状态错乱。

**建议**

放置建筑时不仅检查居民当前格，还检查每个居民剩余 `path` 是否经过新建筑占格；
命中则让居民重新寻路或调用 `evict_out()`。另一种做法是在 `_move()` 每步检查
下一格是否仍可走，不可走就停止并重新决策，但这会让移动逻辑承担放置事件的
后果，建议优先在放置侧处理。

### R-05 [P3] 放置失败时建筑已先加入场景并注册

**位置**

- `Scripts/World/PlacementController.gd:146-158`：先 `add_child(building)`，再
  `place_at()`；失败时只 `queue_free()`。
- `Scripts/Building/Building.gd:70-73`：`_ready()` 在 `is_preview == false` 时
  立即注册到 `TickManager`。

**问题**

`add_child()` 会同步触发 `_ready()`，因此建筑在 `place_at()` 校验之前就已经
进入 `TickManager.buildings`。放置失败后 `queue_free()` 是延迟到帧末执行的，
失败建筑在当帧仍然是一个合法目标，且 `origin_cell` 还是默认的 `(0,0)`。
正常 UI 路径在 `PlacementController.gd:142` 有一次 `_ghost.can_place_at()`
前置检查，所以这条路径概率较低；但 `Building.place_at()` 是公开接口，测试场景、
读档、未来拆除/旋转和状态变化都可能直接走到这里，注册时机仍应修正。

**复现结果**

让一栋取水站以非法坐标 `(-100,-100)` 调用 `place_at()`：

```text
failed place=false registered=true
```

失败建筑仍然在 `TickManager.buildings` 中。

**影响**

如果同一帧稍后发生 tick，居民可能把失败建筑当成取水/取食/工作目标，走向
世界左上角一个不存在的出入口；目标随后被释放，居民会再回到闲置。这个问题
在连续点击非法位置时更容易出现，也会污染建筑详情页的连接关系。

**建议**

先创建临时建筑并完成 `can_place_at()` 校验，校验通过后再 `add_child()` 和
`place_at()`；或者在失败分支立即 `TickManager.unregister_building(building)`，
并避免在成功前设置正式节点名。

### R-06 [P3] 权重平手时的优先级与注释相反

**位置**

- `Scripts/Human/Human.gd:240-252`：注释写“平手时优先级：水 > 食物 > 工作”，
  但代码先把 `WORK` 放进 `best_goal`，再用严格大于比较水/食物。

**问题**

当 `water_weight == WORK_WEIGHT`（文档所说的“还剩 36 分钟，刚好追平工作”）
时，`water_weight > best_weight` 为 `false`，工作继续胜出。食物与工作平手时
同样如此。实际优先级是“工作 > 水 > 食物”，与注释和 `Docs/总/资源` 的预期相反。

**影响**

居民会在刚好达到补给阈值时继续工作，最多再等一个 `DECISION_INTERVAL`（5 刻）
才出发。数值影响不大，但这是核心决策逻辑与文档不一致，后续调参时容易误判。

**建议**

按“水 → 食物 → 工作”的顺序比较，水/食物使用 `>=` 并加正值保护，或者先选出
水和食物的较大者，再用严格大于与工作比较。

## 四、非阻塞问题与文档同步

以下问题不改变当前主流程，但会让调参和后续开发误判，建议顺手修正：

1. `Scripts/Core/TickManager.gd:9-10` 仍写“1.4 米/秒 × 12 ≈ 17 格/刻、一天
   三十公里”，但 `Human.WALK_CELLS_PER_DAY = 750`，实际换算约为
   `750 / 1800 = 0.4167` 格/刻；两套说法会误导改速度的人。
2. `Scripts/Core/TickManager.gd:28` 写“一天 6 小时 ÷ 300 刻 = 72 秒”，
   `TickManager.gd:31` 写 `0 ~ 299`；当前 `TICKS_PER_DAY = 1800`，
   每刻 12 秒、当天第 0 ~ 1799 刻。
3. `Docs/v0.0.1a/实现说明.md:12` 仍写“16.8 格/刻、一天三十公里”，
   与当前实现不一致；`:74-78` 仍描述“所有图形都是代码画的、衣服颜色表示状态”，
   但现在居民已经是 Blender 序列帧，颜色由 `Outfit` 预设决定。
4. `Tools/Blender/make_human.py:6-11` 的产物说明仍指向
   `Assets/Human/blue/idle_0.png`，实际已改为 `side/down/up` 三视角目录。
5. `Scripts/Grid/WorldGrid.gd` 使用 4 个空格缩进，不符合 `AGENTS.md` 要求的
   GDScript Tab 缩进；当前能运行，但后续编辑混用 Tab 时容易产生缩进错误。
6. `Scripts/UI/BuildingDetailPanel.gd:130-162` 每个 tick 都 `queue_free()` 旧控件
   后立刻重建；高倍速（例如 `--speed=600`）下会在一帧内堆积多次 UI 重建，
   面板打开时有明显的内存/布局开销。可改为复用 Label，或按需重建。

## 五、建议修复顺序

1. **R-01**：恢复虚弱状态，这是行为规则回归，优先级最高。
2. **R-02 + R-03**：先保证建筑放置不会破坏已有出入口，再让居民在最近目标
   不可达时尝试可达的同类建筑/其他出入口。
3. **R-04**：放置建筑时处理居民剩余路径，避免穿模。
4. **R-05**：调整建筑创建/注册顺序，避免失败建筑残留。
5. **R-06**：统一平手优先级。
6. 最后同步本报告第四节的注释和文档。
